## 1. スケール — 実測値と、いつ壊れるか

2倍・5倍・10倍・100倍のコーパスを合成して**実際にビルドを回した実測値**。
再取得にはそれなりの時間が掛かるので、数字をここに残す。

### 到達可能性（＝これが優先度を決めている）

`scripts/sync-pubmed.ts` の `MAX_NEW_PER_RUN = 50` と週次実行から:

| | 上限いっぱい | 実勢（約20件/週） |
|---|---|---|
| 1,102 → 11,000（10倍） | 3.8年 | **9.6年** |
| 1,102 → 110,000（100倍） | 42年 | 約105年 |

さらに検索式のヒット数は90日あたり約229件（年間約930件）。
**該当する文献が世に11万本存在しない。100倍は現実の軌道ではない。**

→ **10倍に到達するのは、過去文献の一括収集を意図的にやると決めた場合だけ。**
そのときに最初に壊れるのは以下の3つで、**BM25ではない。**

### 10倍で最初に当たる壁

| # | 場所 | 実測 | 10倍で | 壁 |
|---|---|---|---|---|
| S1 | `out/` のファイル数 | 198MB / **10,117ファイル**（論文1本あたり9.0ファイル・176KB） | **2.0GB / 99,541ファイル** | Vercelの1デプロイあたりファイル数上限が10万前後。**約11,100本で当たる** |
| S2 | `data/papers.json` のgitサイズ | 3.9KB/本 | **43MB** | GitHubは50MB超で警告（**約12,800本**）、100MB超でpush拒否（**約25,600本**） |
| S3 | `/papers` の配信量 | 3.5MB生 / **721KB brotli**。内訳は `abstract` 63% + `abstract_ja` 17% = **80%が抄録** | 約7.2MB brotli | 低スペック端末で読み込み不能 |

S1の内訳: ページHTML 59KB + RSC 26KB + セグメントキャッシュ7ファイル52KB。
**セグメントプリフェッチの7ファイルがバイト数の30%・ファイル数の78%**を占める。

### 100倍で壊れるもの（到達しないので参考）

| # | 場所 | 1,104件 | 11,040件 | 110,400件 |
|---|---|---|---|---|
| S4 | `lib/related-papers.ts` の索引構築 | 0.26s | 2.23s | 28.7s |
| S4 | 同・全クエリ合計 | 0.42s | **59.6s** | **18,759s ≒ 5.2時間** |
| S4 | 同・索引のヒープ | 10.4MB | 224MB | 1.44GB（総ヒープ2.84GB） |
| S5 | `lib/papers-search.ts` の索引構築（初回打鍵時・同期） | 145ms | **1.29s** | **13.2s** |
| S6 | 絞り込み1操作（全配列を12回以上走査） | 8ms | 55ms | 560ms |
| S7 | `app/papers/[id]/page.tsx:32,48` の `papers.find()`（1ページ2回×N） | 27ms | 3.5s | 7.2分 |
| S8 | `PaperFilters.tsx` の `Math.min(...ys)` | — | — | 20万要素で `RangeError`（12.5万は通過） |

**S4 の診断: 転置索引は枝刈りしていない。** 1クエリあたり実際にスコア計算する論文は
全体の **96.5%**（10倍で98.1%、100倍で99.3%）。`MAX_DF_RATIO = 0.25` のため
1語のポスティングがN/4まで伸び、漸近的には全ペア走査と同じ O(N²)。
直すなら BM25 の改良ではなく**候補生成を絞る**（元論文のIDF上位k語だけ辿る、
近傍を増分で事前計算する）。

A/B実測: 10倍で関連研究を空配列にすると静的生成 92秒 → **45秒**、`out/` 2.0GB → 1.5GB。
**関連研究だけで10倍時の静的生成の51%。**

### 触ってはいけない（実測で問題なしと確認済み）

- **モジュール索引キャッシュは効いている。** 実ビルドで `buildIndex` の呼び出しは
  ちょうど3回（静的生成ワーカー1つにつき1回）。ページごとではない。
- **クライアントにデータは出ていない。** `out/_next/static` は総計1.2MBで、
  papers.json も topic-areas.json も含まれない。
- `ListPaper` の許可リスト、クライアント側20件ページング（DOM一定）、
  検索索引の遅延構築、`CANDIDATE_K = 15`（詳細ページのサイズがNに依存しない）。
- 収集は Set で O(N)。`validate-papers.ts` は線形（100倍でも6.6秒）。
- 診療分野のビルド毎再計算は全スケールで安い（6ms → 23ms → 360ms）。

## 調べた結果、問題ではなかったもの

**同じ疑いを持ったときに調べ直さないこと。**

| 疑い | 実際 |
|---|---|
| 「トピックが null の6件は永久に埋まらない」 | **誤り。** OpenAlexに問い合わせ直した結果、2件は収集翌日にすでに付与済み（次回backfillが自動で埋める＝設計どおり）、3件はOpenAlex側にトピックが無い、1件はOpenAlexに未収載。**バグは0件** |
| 「backfill の終わらない再試行ループ」 | **設計。** それが上記2件を救っている仕組み。コストは週数リクエスト |
| 「404で既存の良いデータが潰される」 | 機構は実在するが（V4）、トピックを持つ論文40件の実測で404は**0件**。理論上のリスク |
| 「`/papers` のプリレンダ放棄はバグ」 | **バグではない。** `useSearchParams` + 静的エクスポートの必然で、絞り込み状態をURLに載せる設計の代償。`out/papers.html` に `BAILOUT_TO_CLIENT_SIDE_RENDERING` が出るのはこのため |
| 「papers.json は挿入順で日付順ではない」 | **誤り。** `entrez_year` 降順 → `entrez_date` 降順で正しく整列している（同日の論文が多いだけ） |
| 検索がユーザー入力で例外を投げる／ReDoS | **無し。** `ASCII_TERM` と `escapeRegExp` の二重防御。正規表現メタ文字9パターンで確認 |
| クライアントバンドルへのデータ漏洩 | **無し。** 全 `"use client"` からのインポートグラフを追跡して0本。`out/_next/static` を grep しても論文本文・トピック辞書とも含まれない |
| URL状態の往復が壊れる | **破れなかった。** `傾向スコア (PSM/IPTW)`、`page=0/-3/abc/999`、`totalPages===0`、未知の `sort` すべて正常。ページ番号の丸め込みはURLにも書き戻される |
| お気に入りのハイドレーション不整合 | **無し。** `useSyncExternalStore` に本物の `getServerSnapshot` を渡す教科書的な実装 |
| 抑制ディレクティブ（`@ts-ignore` 等）で握りつぶしている | **1件も無い。** `@ts-ignore` / `@ts-expect-error` / `eslint-disable` / `any` 注釈 / 非nullアサーション `!` がゼロ。`next.config.ts` に `ignoreBuildErrors` も無し |
